# 設計判断の記録（design decisions）

「なぜそうしたか」を理由・利点・欠点つきで残す。用語は [glossary.md](glossary.md)、コードの場所は
[architecture.md](architecture.md) を参照。各判断は時系列でなくテーマ別。

**記入様式**（テンプレ decisions.md 準拠・§35 以降の新規エントリに適用）:
`## N. タイトル（YYYY-MM-DD）` の見出しで、本文に **決定**（何を選んだか）・**理由**（なぜか）・
**却下した代替案**（あれば）を含める。既存 §1〜34 は参照が張られているため見出しは変更しない。

## 1. 操縦に ISMCTS を使う（heuristic ではなく）
- **背景**: heuristic 操縦は**特性・効果・トレーナーを使わない**（攻撃ダメージで殴るだけ）。エンジンは
  それらを合法手として出すのに heuristic は拾えず、デッキ評価が「殴るデッキ」しか正しく測れない。
- **判断**: 合法手を列挙して価値で選ぶ **ISMCTS** を操縦にする（元から特性対応）。
- **利点**: 特性/効果駆動のデッキも正当に評価できる。**欠点**: 遅い。
- 関連: 探索(league)は速度優先で弱め設定、判定(gate/eval)は強め設定、と使い分ける。

## 2. NN 操縦を「蒸留 → improve」の2段で育てる
- **蒸留(distill)**: ISMCTS 教師を真似て**安定した床**（≈ISMCTS）を作る。
  - 利点: 弱いネットからの自己対戦崩壊を回避。欠点: **教師を超えられない**（天井＝五分）。
- **improve(self-play)**: 蒸留床を**種**に自己対戦。MCTS(ネット) はネット単体より強い（方策改善演算子）ので、
  その手を学べば**教師=ISMCTS を超えられる**。
  - なぜ以前の自己対戦は崩壊したか＝**弱いネットから始めたから**。≈ISMCTS の種＋best保存＋低LR＋
    replay＋drift安全弁で安定させる。
- **改善ループは `improve ↔ ratchet-nn`**（`distill ↔ improve` ではない）。
  - 理由: improve で ISMCTS を超えた後に distill へ戻すと、**教師=ISMCTS の天井(五分)へ引き戻して**
    improve の成果を消すから。distill は最初の土台作りの一度きり。

## 3. 探索は少数メタ・判定は gauntlet（過学習対策）
- **背景**: 少数のサンプルメタだけに最適化したら Kaggle 順位が悪化＝**過学習**。
- **判断**: 探索(league)は速い少数メタ、**判定(gate/eval-deck)は多様な gauntlet**（メタ＋チャンピオン系＋
  全色 mono-type）に分離。過学習の歯止めは判定側で掛ける。
- **限界**: gauntlet も**代理指標**。実戦(Kaggle)で単調改善する保証はない（issue #3 で監視）。

## 4. keep-best ラチェット（後戻りしない蓄積）
- **背景**: league 内部評価は小サンプルでノイズが大きく「より弱いデッキへ更新」してしまう。
- **判断**: league 出力を多めの試合のゲートに通し、**現ベストを確実に上回った時だけ** `champion_best` を更新。
- **効果**: 回すほど単調改善・ノイズで劣化しない。提出は `champion_best` を使う。

## 5. 蒸留の方策ターゲットを温度で one-hot↔soft 1本化
- **背景**: soft-π（訪問分布）を一律に使ったら**逆効果**だった（あるデッキ 0.45→0.20）。原因は蒸留の
  教師探索が**浅く訪問が平坦**で、soft-π が無情報な的になったこと。
- **判断**: `π ∝ visits^(1/τ)` の**温度 τ** で統一。**既定 τ=0（one-hot・安全）**、教師を深くしたとき
  `τ>0` で soft を解放。one-hot を特例として内包＝「悪くなりようがない」。
- **要点**: soft-π は **深い教師（time_budget↑ / iters_per_det↑）とセットでないと効かない**。
- **one-hot の欠点も理解しておく**: 迷う局面（僅差）を捨てて過信しやすい・tie-break ノイズを確信として
  焼き込む・情報量が少ない。あくまで「浅い教師での安全な既定」であって最良ではない。

## 6. best 選抜を全学習デッキの平均で行う
- **背景**: NN が「ある学習デッキでは ISMCTS 超え、別デッキでは負け越し」＝**汎化不足**。原因の一つは
  best 選抜が**eval 固定1デッキだけ**で、その1デッキに偏った snapshot を選んでいたこと。
- **判断**: eval/best 選抜を**全学習デッキの平均勝率**に（1デッキ最低10試合でノイズも抑制）。
- 関連: issue #2。

## 7. 収集の CPU 並列化（GPU ではなく）
- **背景**: 「1回の学習でもっと試行回数を増やしたい」。
- **判断**: 各対戦は独立なので **ProcessPoolExecutor で CPU コアに分散**（≈コア数倍）。
- **なぜ CPU か**: NN-MCTS は **batch=1 の小さなネット推論＋エンジンのフォワードシミュレーション**で
  CPU 寄り。GPU の batch=1 は転送オーバヘッドでむしろ遅い。学習（大バッチ）だけ GPU。
- **なぜ spawn か**: 親が CUDA を初期化済みだと **fork はハング**しうる → **spawn** で回避。
- **worker 数の既定 = nproc-1**: 1コアを OS/GPU供給に空けて機械の無反応を防ぐ（HT環境なら物理コア数推奨）。

## 8. run を跨いで蓄積する（best の永続化）
- **判断**: `--resume` で作業ネットを継ぎ足し、best の基準勝率を `*.meta.json` に**永続化**。
  - これが無いと再開のたびに best 基準が -1 にリセットされ、**劣化モデルで best を上書き**してしまう。
- **蓄積の2種類**: `--resume` は**作業ネット**を継ぐ（最新の学習を活かす＝普通はこれが正しい）。
  `*_best.pt` は**選抜専用の安全な snapshot**で、学習の継ぎ足しには使わない。

## 9. improve の drift 安全弁（`--resume-from-best`）
- **背景**: 自己対戦は作業ネットが drift（悪化）しうる。`--resume` は作業ネット継続なので悪化も蓄積しうる。
- **判断**: 再開時、作業ネットの直近 eval が best を margin 超で下回っていたら **best から再開**
  （人の「悪い癖がついたら良かった頃へ戻す」）。improve のみ有効、distill は安定なので対象外。

## 10. 蓄積（継続学習）のデメリット
- ネットは固定サイズ＝**容量飽和**でいつか頭打ち（人と違い脳は増えない）。
- 同じ学習デッキへの**過学習**（→複数デッキ選抜で緩和）。
- デッキ軸の単調性は**gauntlet 基準**であって**実戦で単調とは限らない**。
- replay buffer は直近のみ保持＝**サンプルは新陳代謝・重みは蓄積**（意図的）。

## 11. 提出物には「操縦」も含まれる
- 提出は「デッキ持参＋毎手プレイするエージェント」＝**操縦は提出の中核**（デッキだけではない）。
- 現状は ISMCTS 操縦で固定。**NN が ISMCTS を安定して超えたら**、提出操縦を NN に切替えられる
  （build_submission に nn モジュール＋`.pt` を同梱・要 torch）。だから NN 強化は提出に活きる（issue #4）。
- 公式サンプルに AlphaZero 型 MCTS があり、提出環境で torch/NN が使える見込み（要最終確認）。

## 12. 速度の正しい理解（誇張しない）
- `ratchet-nn`（NN 操縦の探索）は「**速度**」ではなく「**探索の質**」の改善。現行 ratchet の ISMCTS は
  速度優先で弱い設定（探索が雑）なので、NN-MCTS のほうが per-move では遅くても**評価が賢い**。
- 「NN は ISMCTS の約1/4時間」は**同じ強さの ISMCTS と比べた話**。弱い設定の ISMCTS とは前提が違う。

## 13. 効果文を「読んで数値カテゴリ化」する（NN v2・規約上OK）
- **背景**: 当初「効果文（Pokémon Element）は読まない」と過剰に自主規制し、NN が手の効果を理解できず
  policy が手を順位付けできなかった（champion で 0.15 など）。
- **規約の再確認**: 効果文を**モデルの学習/推論に使うのは許諾の範囲内**（ルール L73）。禁止は
  **公開・再配布**（L81/L190）と競技外利用のみ。派生した数値や重み・embedding は参加者の生成物で
  Pokémon Elements ではない（L306）。→ **読んでよい。出さない（commit/公開しない）だけ。**
- **判断**: エンジン JSON の attack/skill `text` を**汎用ゲーム機構のキーワード**で効果カテゴリ
  （draw/heal/KO 等10種）のビットフラグに変換（`cards._effect_bitmask`）。生テキスト・カード名は保持/出力しない。
- **効果（実測）**: champion vs heuristic 0.15→0.4台・vs ismcts 0.15→0.45 と**カタストロフィ解消**。

## 14. cardId 埋め込み＋容量↑（NN v2・表現力を上げる）
- **背景**: 数値特徴だけでは「カード固有性」を粗くしか表せず、小さいネット（hidden256・2層）は
  ISMCTS を真似きれず**教師より下**（40試合で heuristic/ISMCTS 未満）で頭打ち＝**容量・表現の限界**。
- **判断**: 特徴ベクトル**末尾に整数 cardId** を載せ（features の `N_STATE_ID`/`N_ACTION_ID`）、net が
  分離して **Embedding**（`net.PVNet`・card_emb16・共有・pad0）。容量も hidden512・trunk3層に拡張。
  Sample/encode の型は不変（id は float 配列の末尾に同居）＝侵襲最小・warm-start 契約は廃止（再学習前提）。
- **狙い**: 学習でカード固有の有用性を捉え、ISMCTS を**真似きる→超える**表現力（prize-zone の核）。
- **訂正（2026-07-02・撤回）**: この拡張は**裏目**だった。診断で policy が一様（教師再現度 0.10≈偶然・
  max prior 0.16）＝**大容量が蒸留データ量（数デッキ・~1万サンプル・登場 cardId 数十種）に対して過大**で
  未学習と判明。1300 カード埋め込みの大半が初期値のまま。→ **埋め込み撤去・hidden256/2層に right-size**
  （`card_emb=0` で埋め込みは将来データ増時に解放可）。汎化する効果/KO/弱点 float 特徴は残す。
  **教訓: 容量はデータ量に合わせる**（[現在地](#現在地と次の判断2026-07-02)）。

## 15. 接地 floor（net 非依存で pilot ≥ heuristic を保証）
- **背景**: NN-MCTS は MAIN/ATTACK 以外を heuristic にフォールバック。半端な net は攻撃選択を悪く
  上書きし **heuristic を下回る**。しかも net の value が誤るデッキでは**探索を増やすほど悪化**（救えない）。
- **判断**: NN の手と heuristic の手が違うとき、両者を**heuristic ロールアウトで実地比較**
  （`ismcts.evaluate_actions_by_rollout`）し、**接地評価で heuristic を上回る時だけ NN 手を採用**
  （`nn_mcts` の `floor_rollouts`）。net が間違っても pilot は heuristic を下回らない。
- **効果（実測・champion・floor=8）**: 素 net 0.25→pilot **0.575**(vs heuristic) / 0.175→**0.45**(vs ismcts)。
  net 非依存の安全弁で**≥heuristic・≈ISMCTS の使える pilot**が即完成。推論/評価/提出向け（収集では未使用）。

## 16. 特徴 v2.1（サイド価値・有効ダメージ・tera）— ex の2枚取りを明示
- **背景**: Kaggle リプレイで気づいた欠落。**ex は KO でサイド2枚・megaEx は3枚**取られるが、特徴は
  `is_special`(ex/mega/tera/aceSpec 一括の bool)だけで**枚数を区別せず**、行動側に「この KO=何枚」も無かった。
  さらに **KO 可能フラグが基礎ダメージ**で、弱点×2/抵抗−30 を織り込まず「弱点で倒せる/抵抗で倒せない」を誤っていた。
- **判断（cards.py / features.py）**:
  - `prize_value`（**megaEx=3 / ex=2 / それ以外=1**・ex/megaEx フラグ由来）と `is_tera` を追加。tera は
    **prize ではなくベンチ無敵**（ベンチのワザダメージ無効）なので prize と**独立**に扱う（tera非ex でも prize は正しく1）。
  - ポケモン特徴（active/bench 両方）に prize_value/tera/appearThisTurn/maxHp絶対/抵抗有無 を追加。
  - 行動の相互作用を **有効ダメージ**（弱点×2・抵抗−30）で再計算し、**KOサイド報酬（=KO可能×相手サイド価値）**
    を明示。これで NN は「弱点を突いて ex を倒す2枚取り」を直接評価できる。
- **注意**: 効果は NN の特徴層のみ。**ISMCTS/エンジンは元から弱点・抵抗・サイドを正確に処理**（提出=ISMCTS は影響なし）。
  弱点×2/抵抗−30 は標準近似（エンジンが真値）。特徴次元が変わるため**旧 net は無効＝床を一度作り直す**。

## 17. best 選抜は「loss 最小」でなく「eval 勝率」で行う
- **疑問**: eval 間の iter から**loss 最小**を選んで eval すればよいのでは？ 最新 iter で eval する必要は？
- **却下理由（loss は選択基準に使えない）**:
  1. **loss は強さの弱い代理**。低 loss ＝教師 argmax への過学習で**むしろ弱くなりうる**。policy_loss には
     教師の決定エントロピー分の**下限**があり、value_loss は容易に 0.05 まで落ちる＝**loss 最小 ≠ 最強**。
  2. **iter 間で比較不能**。毎 iter リプレイバッファが入れ替わる＝**測っている問題（データ）が違う**。
     「loss 最小 iter」は「バッファがたまたま簡単だった iter」を拾っているだけかもしれない。
- **方針**: 選択は**実目的＝eval 勝率**で（best-gate・CRN＋確認評価）。loss は進捗の**安価な診断**にとどめる。
- **なぜ最新 iter で eval**: 学習は逐次で次は最新から続く＝**最新が軌跡の現在地**。非最新の「loss 最小 iter」を
  採るには全 iter 保存＋ロールバックが要り、基準も loss（弱い代理）＝二重に損。best-gate は eval で拾うので
  良い iter は失われない（loss が上がっても最新で eval するのは、**loss を選択に使っていない**から）。
- **iter ノイズの正しい対処**: eval を厚く（試合数↑・CRN・確認評価＝実装済）か、**重み平均（EMA/SWA）**で
  SGD ノイズを均す。loss 選抜ではない。関連 [glossary: 重み平均](glossary.md#重み平均ema--swa)

## 18. improve 改修（深い収集＋Dirichlet 根ノイズ）— 横ばいの対策
- **背景（2026-07-03 実測）**: improve 90 iters（~12h・sims=64/dets=2）で raw eval 0.40〜0.46 の横ばい。
  floored でも種（distill_best 0.575/0.600）を超えられず（0.450/0.575）＝**利得ゼロで撤退基準に該当**。
- **診断**: improve の学習信号は「**探索後の soft-π − 素の policy**」の差分。素の policy が平坦なうえ
  sims=64/dets=2 の浅い探索では π も大して賢くならず、**「ほぼ自分を自分に蒸留」**して横ばいになる。
  相手も自分（弱い者同士）で value の勝敗ターゲットも情報が薄い。
- **改修（3点）**:
  1. **収集専用の探索深度** `--collect-sims/--collect-dets`（improve 既定 collect-sims=128）: 収集だけ
     探索を深くして教師の質＝差分を太らせる。eval/推論の深さは従来のまま。**iter は重くなる（質＞回数）**。
  2. **Dirichlet 根ノイズ** `--root-noise`（既定 ε=0.25・AlphaZero 標準）: 根の priors に
     `P←(1−ε)p+εη, η〜Dir(10/手数)`。self-play の探索が毎回同じ手に固まるのを防ぎ、データの多様性
     ＝改善オペレータの探索範囲を保つ。**推論/評価には掛からない**（強さを測る時は決定的）。
  3. **弱い improve 資産の退避**（models/attic/）: NN_NET/EVAL_NET が improve_best を自動優先するため、
     種より弱い improve_best が黙って使われる事故を防ぐ。次の improve は distill_best から再出発。
- **教訓**: self-play は回せば強くなるのではなく、**「探索が素の方策より賢い」条件が崩れると空転する**。
  空転の兆候は eval_winrate の横ばい（loss は下がり続けるので当てにならない・[§17](#17-best-選抜はloss-最小でなくeval-勝率で行う)）。

## 19. 提出操縦の NN 対応（issue #4・floored NN-MCTS＋時間ガード）
- **背景**: 提出アダプタは ISMCTS/heuristic/random のみ対応だった。floored NN が ISMCTS を超えたので、
  提出操縦も NN 化して実戦成績に反映する（[design 11](#11-提出物には操縦も含まれる)）。
- **判断**: improve の成否に関わらず**一度だけ実装**（現 floored NN が既に ISMCTS 超えのため作る価値がある）。
  - `make_kaggle_agent("nn")`＝**floored NN-MCTS**（[design 15](#15-接地-floornet-非依存で-pilot--heuristic-を保証)）。
  - **torch は nn 選択時のみ遅延 import**（ismcts/heuristic 提出は torch 不要のまま）。net は常に **CPU** 読み
    （batch=1 は CPU が速く、提出環境の GPU 有無に非依存）。
  - **時間ガード**: NN-MCTS は sims 固定で自前の時計を持たないため、累積消費が game_budget(540s) を超えたら
    heuristic（瞬時）へ退避＝**600秒クロックの時間切れ負けを防ぐ保険**（[glossary: 提出の時間管理](glossary.md#提出の時間管理game-budget--時間ガード--600秒クロック)）。
  - `make submission-nn`（最良 net = improve_best>distill_best 自動選択）・`make smoke-submission`（実対戦で
    時間実測）。NN 系モジュールは常に同梱（遅延 import なので ismcts 提出でも無害）。
- **注意**: 提出環境の CPU はローカルより遅い可能性。煙テストで 2倍以上の余裕を確認してから提出する。

## 20. gate の上振れ昇格対策（mean ガード＋確認評価）
- **実測の事故**: ratchet-nn の gate（20試合）が worst +0.05 / **mean −0.077** の候補を昇格させた。
  40試合・別シードの再戦では旧チャンピオンが明確に上（mean 0.697 vs 0.571）＝**ノイズドリフト昇格**だった。
- **原因**: worst（min-of-16）は最もノイズが乗る統計量（1相手 SE≈0.11）なのに、旧ルールは
  「worst が margin 超で勝てば mean を見ずに昇格」。さらに**エンジン内部のシャッフル乱数は外から
  シードできない**ため、同一シードのペア比較でも対戦条件は完全一致しない（run 間の揺れが大きい）。
- **対策（champion_gate.py）**:
  1. **mean ガード**（`--mean-guard` 既定 0.05）: worst で勝っても mean がこの幅を超えて劣化していたら
     不採用（今回の事故はこれだけで防げた）。
  2. **確認評価**（既定 on・`--no-confirm` で省略）: 昇格候補が出た時だけ**別シードで再評価**し、
     両方で勝った時のみ昇格。**コストは候補が出た時だけ2倍**＝据え置き run は従来コストのまま。
- **教訓**: [§17](#17-best-選抜はloss-最小でなくeval-勝率で行う) と同型。「1回の eval で意思決定しない。
  昇格・採用の判断には必ず独立な再現を要求する」。worst-case 目的は正しいが、**worst の数字は
  平均より桁違いに揺れる**ことを常に織り込む。

## 21. 大きな投資（GPU日単位）の前の判断基準
- **背景**: 「盤面特徴 v2.3 を実装すべきか」の議論で、慎重さの根拠を明文化した。
- **このプロジェクトの実績（基礎率）**: 「NN に足す」投資は勝率が悪い——埋め込み＋容量↑(悪化・撤回)、
  soft-π(悪化・撤回)、深い収集(実験で棄却)、improve 90iters(利得ゼロ)、混合プール(効果検出できず)。
  効いたのは**直す・測る・削る**——right-size、強教師、floor、根ノイズ＋fresh種、eval ノイズ除去、
  実メタ較正、gate 強化。「足せば良くなるはず」には自動的に懐疑をかける。
- **投資前チェックリスト**:
  1. **メカニズムレベルの診断があるか**（「なんとなく弱い」でなく「value が盤面に盲目」のような特定）。
  2. **因果の鎖を書き下し、各環の検証状態を確認**（例: 特徴追加→valueが学ぶ→**手が変わる**→勝つ。
     どこか一つでも未検証の環があれば、そこを先に安く検証できないか考える）。
  3. **もっと安い代替検証があるか**（例: 学習させる前に、手作りの補正を value に注入して効果の上限/下限を測る）。
  4. **成功基準と撤退基準を事前に決める**（何 iters・どの指標がいくつなら継続/打ち切り。
     sunk cost での grind を構造的に防ぐ＝improve 90iters の教訓）。
  5. **機会費用**: 同じ GPU 時間で他にできることが尽きているか（デッキ軸・計測系の安い改善が残っていないか）。
- **慎重≠不作為**: 証拠が揃えば（敗因分布の安定・他の投資先の頭打ち・診断の確定）、基準を満たした投資は
  迷わず実行する。このチェックリストは「やらない理由」でなく「やるなら勝てる形にする」ためのもの。

## 22. 盤面特徴 v2.3（board-blind の恒久修正・§21 の実践）
- **経緯**: value の盤面感度 ≈0（[§18 後の診断]）→ §21 のチェックリストに従い、**学習の前に注入テスト**
  （value に `α×(自駒−敵駒)/5` を外挿・40試合×α スイープ）で因果の最後の環を検証:
  **vs ismcts が α に厳密単調増加（0.450→0.500→0.525→0.575）・α=0.2 で平均 +0.075・0.3 で頭打ち** ＝ GO。
  即効処置として α=0.2 の注入を提出・判定に配線済み（[design 19](#19-提出操縦の-nn-対応issue-4floored-nn-mcts時間ガード)の拡張）。
- **v2.3 の設計**（このブランチ）:
  - **特徴 5 float**（`BOARD_FEAT`・**末尾 cardId の直前**に追加）: 自分/相手の場の駒数・**駒数差
    （注入で実証したシグナルそのもの＝value は重み1個で拾える）**・手札のたね数・総資源。
  - **warm-start が成立する配置**: id 列は net が捨てるため、id 直前への float 追加は旧 float 列の位置を
    変えない。旧重みを先頭コピー＋新列ゼロ初期化＝**学習開始時の挙動は現 net と同一**（床の再蒸留は不要）。
  - **学習経路**: 収集評価器にも α=0.2 を注入（`--collect-board-bonus`）＝「盤面を読む探索」の訪問分布を
    net に蒸留（AlphaZero の償却）。value は明示特徴＋勝敗ラベルから盤面感度を回帰。
- **事前登録基準（改修 improve 30〜60 iters 後）**:
  - 成功 = (a) diagnose_value_board で**盤面感度 ≥ +0.05**（現状 +0.012）かつ
    (b) **注入なしの新 net ≥ 注入ありの旧 net（vs ismcts 0.575 目安）** → 注入を撤去し学習版へ置換。
  - 撤退 = 感度 < +0.03 or 強さ改善なし → 注入運用を継続し v2.3 は打ち切り（注入が既に価値の大半を回収）。
- **検証1回目（2026-07-07）は無効試合**: improve_best(EMA) が旧 seed と小数第3位まで一致＝
  **EMA の減衰率バグ**（per-step 前提の 0.999 を per-iter 更新に適用→0.999^30≈0.97 で学習が実質凍結）。
  EMA 導入以降の improve_best は全て「ほぼ種」だった（過去のプラトーの一部を遡って説明）。decay を
  0.9 に修正して再検証。教訓: ①移植したハイパーパラメータは**更新頻度の前提**ごと確認する
  ②同一 net 疑いは「数値が一致しすぎる」ことから検出できる（差分 B−A を主指標にする）
  ③盤面感度の絶対値は進行役 heuristic の局面分布に交絡する＝**新旧の差分だけが有効な信号**。

## 23. self-play 崩壊の診断と対策（温度スケジュール）
- **実測（2026-07-07）**: EMA 凍結バグ（[§22 追記]）を剥がして生 net を測ると、v2.3 improve 30iters の
  生 net は**種より弱く（floored vs ismcts 0.675→0.425）**、盤面感度は**逆相関**（B−A: 盤面 −0.09/危険 −0.105）。
  self-play は「学ばない」でなく「壊していた」。
- **原因（データ生成の毒）**: 手選択を**全手 π サンプリング**していた。浅い探索（64sims/2dets）の平坦な
  π から終盤に悪手を引き、「勝勢だったのに乱心で負けた」試合の z が全局面に付く → value が
  「盤面が薄い側が勝つ」という**データに実在する偽相関**を正しく学習してしまう。ネットや符号の
  バグではなく**教材の質**の問題（だから「逆を実装」しても直らない）。
- **対策（AlphaZero 標準に揃える）**:
  1. **温度スケジュール**（`--opening-samples` 既定12）: サンプリングは序盤 N 決定のみ・以降 argmax
     ＝対局の質を保ち z の汚染を止める（本命）。
  2. **収集の盤面補正を既定 OFF**（`IMPROVE_COLLECT_BONUS=0`）: 未検証要素の切り分け（§21 一度に一変更）。
  3. **カナリア評価**: eval のたびに**生 net** も先頭デッキで測って表示＝EMA が劣化を隠す事故を構造的に防ぐ。
- **成立条件の言語化**: self-play が機能するには「探索 > 素の方策」（§18）に加えて
  **「対局の質が z を信頼できる水準に保たれる」**が必要。温度スケジュールは後者の担保。

## 24. NN 学習ラインの凍結 — 「データに無い信号は学べない」
- **4経路すべてが同じ結論**: 盤面感度（盤面差が勝敗に効くという value の学習）を、
  ①self-play ②混合プール ③v2.3 明示特徴 ④教師あり distill の**独立4経路すべてで動かせなかった**
  （B−A 感度差 ≈0、時に逆行）。強さ（floored vs ismcts 0.575〜0.6）は保たれるが、盤面理解は不変。
- **最終診断**: ベンチ切れは**実戦の相手分布の現象**（相手が薄い盤面を罰する）で、ISMCTS 同士の
  質の高い対局データには稀（互いに上手く補充する）＝**信号がデータに存在しない**。特徴を与えても
  教師ありでも、データに無い相関は学べない。self-play は加えて「量の壁」（z の試合相関・§23）で崩壊。
- **含意の逆転（§22 の前提を反転）**: 「注入は暫定・学習版で置換」ではなく、**注入（盤面補正α0.2）を
  恒久解として正式採用**する。**学習で獲得できないドメイン知識は、検証済みの事前分布として注入する**
  ——これが本プロジェクトで得た最大の一般教訓。
- **決定**: NN の学習ラインを凍結（operative net = seed 由来 v2.3 形式＋注入で運用）。ExIt 案は撤回
  （π/value は改善できても、データに無い盤面信号は ExIt でも作れない＝期限リスクに見合わない）。
  残り時間はデッキ軸（ratchet-nn・実メタ帯）と実戦 A/B（nn_repaired）と提出選択に集中。
- **再開条件（将来）**: 実戦 replay を**訓練データに混ぜる**（相手分布ごと学ぶ＝唯一データに信号が入る道）・
  試合数を桁で増やせる計算資源。

## 25. 実戦 replay を value 学習に混ぜる（データに信号を入れる唯一の道）
- **§24 の裏返し**: 「盤面信号はデータに無い」なら、**信号のあるデータ＝実戦 replay を訓練に入れれば学べる**。
  実戦の z（＝薄い盤面で実際に負けた結果）には信号が入っている。self-play/distill が全滅したのは
  ISMCTS 同士の対局に信号が稀だったからで、相手が本気で薄い盤面を罰す**実戦だけ**が例外。
- **設計（offline value fine-tune）**:
  - `extract_replay_samples.py`: episode JSON の**両席**・全決定局面から (state, z) を抽出し .npz に
    冪等永続化（JSON はこの後削除可）。**相手席も入れる**＝上手い相手が薄い盤面を罰した局面＝信号の本体。
  - `replay_value_tune.py`: operative net を warm-start し **`policy_weight=0` で value 頭だけ** fine-tune
    （我々の手のクローン=自己蒸留・相手の手=雑音で policy を汚さない）。holdout MAE で早期見切り。
- **訓練データ選択の逆説（重要な一般教訓）**: 「良いデッキ」と「良い訓練データ」は別基準。value に
  「薄い盤面＝負け」を教えるには**その故障モードが濃く起きた対局**が要る。故に**エネ過多の弱いデッキの
  replay（ベンチ切れ負け63%）の方が、修正済みデッキ（同25%）より教材として濃い**。value は z だけを学び
  デッキ構成は学ばない＝弱いデッキの対局で学習しても汚染されない。→ **全ソース（nn/nn_repaired/others）を
  混ぜる**（量と多様性が小サンプル value 回帰に効く）。
- **事前基準**: 盤面感度 B−A ≥ +0.05（4経路で一度も動かなかった数字が初めて動くか）かつ floored 強さ維持。
  成功→注入に頼らず value が本物の盤面判断を持つ（提出 net に採用）。失敗→実戦データでも学べない＝
  §24 の「注入が恒久解」が最終確定。**どちらでも決定的な知見**。
- **日次運用に組込**: DL → `make replay-extract` → JSON 削除。サンプルが積み上がるほど効く。
- **結果（2026-07-08・決着）**: 実戦47,625サンプルで value fine-tune。**検証MAE 0.41→0.12＝実戦データに
  信号は実在し value は学べた**（§24の「教師対局には無い」を精密化）。だが**強さは劣化**（vs ismcts
  0.575帯→0.500、穏やか tune でも 0.425）で、盤面感度も強さを犠牲にした時だけ動く用量反応（動かせば
  壊れ・動かさねば学ばない＝良い動作点なし）。**注入 α=0.2 が net を触らず強さを落とさず同じ認識を
  与える**ため実用では注入の完勝。→ **§24「注入が恒久解」が最終確定・NN は operative+注入で凍結**。
- **副産物の価値（低スペック戦略の実証）**: 「実戦データ×分単位の学習」で value が本当に学べたこと自体は
  重要（軍拡でない勝ち筋の存在証明）。今回は注入に負けたが、**将来 policy を実戦データで学ぶ**等の
  低計算・データ駆動の道が生きていることを示す。パイプライン（extract/tune）は資産として残す。
- **組み合わせも測定で棄却（2026-07-08・同一セッション比較）**: replay-tuned+注入0.2=0.450 /
  +注入0.1=0.400 vs **operative+注入0.2=0.675**（vs ismcts 40試合）。注入を弱めても悪化＝二重計上でなく
  **素の value の質が土台で、replay-tune がそれを崩すと注入では埋まらない**。注入は「board-blind な良い
  value」に足すから効く。→ **提出 NN = operative + 注入α0.2 で確定凍結**（測定裏づけ済み）。
- **【重要な訂正・2026-07-08】上記「棄却」はミラー-ISMCTS 測定のアーティファクトだった**: 「replay-tune が
  強さを劣化させる（0.675→0.500）」の根拠は `eval_net.py`＝**同一デッキで NN vs ISMCTS のミラー対戦**。
  この単一・非中立リファレンスを疑い、**外部基準（実メタ16デッキ・非ミラー・eval-deck）で net A/B を測り直した**:
  - champion_best: operative 平均0.469 / replay-tuned 平均0.494（ペア差+0.025・SE≈0.055＝**有意でない**）
  - champion_repaired: 両者とも平均**0.350（完全同点）**
  → **実メタでは operative と replay-tuned は統計的に区別できない**（ミラーで見えた operative 優位は消滅）。
  §25 の「replay-tune は劣化」「NN 章を測定でクローズ」は**誤った測定台に基づく誤結論**。replay-value 経路は
  死んでおらず、依然として生きた選択肢（少なくとも無害・実戦の盤面感度は本物）。
- **プロセスの教訓（デッキ軸の再発）**: **net の比較をミラー-ISMCTS（eval_net）で行ってはいけない**——
  デッキ軸で共適応ロック対策として導入した「外部基準（実メタ・実戦A/B）で測る」原則を、net 軸に当てて
  いなかったのが根因。net の判定も必ず実メタ相手プールで行う（[glossary: ミラー評価の罠]）。
- **恒久対策（警告でなく既定を変える）**: `eval_net.py` の `--vs` 既定を `meta`（実メタ相手プール・非ミラー・
  eval_deck_vs_meta 共用）に変更。ミラー（heuristic/ismcts）は「大まかな確認のみ」に降格し警告を出す。
  「気をつける」ではなく**道具の既定を正しい方に倒す**（受動的な注意書きは再発する）。
- **ただしローカル実メタでも十分ではない**: ローカルプールは実 Kaggle と**デッキも操縦相手も異なる代理指標**。
  net/デッキの最終裁定は依然 **Kaggle 実戦 A/B** に委ねる（gauntlet は proxy metric・issue #3）。
- **replay 収集は「デッキ軸」と「NN軸」両方に効く共通投資**: DL した replay は ①相手デッキ抽出
  （opp_decks・gauntlet-real・determinize 相手推定§26）と ②value 学習サンプル（value_samples・replay-tune§25）の
  **両方**を太らせる。実メタ情報が増えるほど「デッキ強化」だけでなく「NN 強化（盤面信号の学習）」も進む
  ＝日次 replay DL は軍拡でない共通の底上げレバー。詰まって NN 章を再訪する時、サンプルが桁で増えていれば
  replay-value の勝ち目も上がる（今回同点だったのはサンプル 47k・小規模ゆえの可能性）。
- **決定への影響**: 凍結という**行動は無害**（operative は実メタで replay-tuned と同等＝失ったものは無い）。
  提出 net は継続性で operative を維持。ただし理由は「operative が強い」ではなく「両者同等」に訂正。
  replay-tuned は実戦の盤面感度を持つため、**Kaggle A/B 枠が空けば第3変種として試す価値**がある
  （ローカル同点でも実戦のベンチ切れ故障モードでは差が出る可能性）。

## 26. determinize 相手デッキ推定 — 推論時×データ駆動の低計算レバー
- **戦略的位置づけ**: 低スペック環境で訓練の軍拡には勝てない（§25 副産物と同じ問題意識）。だが対局は
  **推論時に 600 秒予算**が全員平等に与えられる＝**推論アルゴリズムの改善は計算格差を中和する**。
  さらに相手推定は `data/replays/opp_decks/`（日次 replay で増える実メタ）を事前分布に使う＝
  **データが増えるほど強くなる**ループで、これも軍拡でない勝ち筋。NN 凍結後の主軸に据えた。
- **問題**: determinize は相手の隠れ札（山札・手札）を仮定してフォワードシミュレーションする。従来の
  `pick_opponent_deck` は候補デッキ群を**ハード整合フィルタ**（可視札を完全に含むデッキだけ残す）＋
  **一様抽選**。中終盤で可視札が増えると完全一致が消えやすく**ミラー仮定へ崩れる**脆さがあった
  （相手が変異 1 枚積んだだけで全候補が脱落）。
- **設計（ソフトなベイズ更新）**: 相手の可視札（捨て札・場・表サイド）を尤度の証拠に、候補 d を
  `weight(d)=exp(-β·misses(d))` で重み付けて比例サンプリング（misses＝d が説明できない可視札枚数、β=2.0）。
  ハード整合＋一様抽選の**厳密な一般化**で、①完全整合（misses=0）は従来どおり最優先、②序盤（可視札少・
  多数が misses=0）は広く一様＝不確実性を反映、③中終盤は自動で真アーキタイプへ収束（belief sharpening）、
  ④完全一致が無くても**最も近い実デッキへ滑らかに縮退**（ミラーへ崩れない）。各 determinization 抽選ごとに
  適用＝探索木全体が「ありえない相手山札」を辿らなくなる。訓練ゼロ・追加計算はデッキ枚数の Counter のみ。
- **配線ギャップの修正**: `build_submission` は候補を `data/*.csv`（5個）からしか同梱していなかった。
  実 replay 抽出の `data/replays/opp_decks/`（79個・実ラダーのメタ）を優先同梱に変更（重複除去）。
  推論の事前分布が初めて実データを反映＝上記ループが機能する前提を満たした。
- **検証**: `tests/test_determinize.py`（ダミー ID・cabt 非依存）で ①完全説明デッキが圧倒（e^-6 差）、
  ②可視札ゼロは一様、③完全一致無しでも最近似へ縮退しミラーに落ちない、④プール空なら従来 fallback、を確認。
- **次**: 実戦 A/B（opp_pool あり/なしの提出）で効果を測る。効けば「β のチューニング」「表サイド・使用
  トレーナー列など可視情報の重み拡張」「ターン跨ぎの belief 保持」へ拡張余地。

## 27. ratchet の実メタ化と高速化（探索の相手＝実メタランダム・gate 軽量）
- **見落としていた本丸**: ratchet の探索（league）の相手は**公式サンプル5デッキ**（`data/*.csv`）だった。
  gate だけ実メタにしても、**探索が的外れな相手に最適化していれば実メタ好adの候補が生成されず**、
  gate は弾くだけで前進しない。「デッキを強くする」なら**探索の相手こそ実メタ**でなければならない。
  ＝共適応ロックの相手プール版（[glossary: 共適応ロック]の破り方＝外部基準を探索にも当てる）。
- **対策（探索）**: 探索 seed を **gauntlet（実メタ）からランダムに SEARCH_SAMPLE=5 抽出**（`shuf`）。
  **top固定でなくランダム**＝毎実行で別の5＝特定デッキへの過適合を回避し実メタ全体に頑健化。
  ＋ champion を試験官に固定（継続性）。gauntlet 無ければ公式サンプルにフォールバック。
- **高速化（害なし）**: 探索の NN-MCTS sims を **64→32**（自前測定 sims32≈64＝強度差なし・§本節）。
  gate は new/best の**相対判定**なので **sims32・floor4・相手は実メタ上位8**に軽量化（floor は両者に
  等しく効き相殺）。GATE_GAMES=20・確認評価は据え置き（誤昇格対策）。**eval-deck（絶対強度の確定評価）は
  提出忠実 sims64/floor8・相手16 のまま**。＝「普段は速く・決め打ちは厳格」の層構成。
- **層構成でのカバー**: 探索5（狭・速）／ gate 8（相対フィルタ）／ eval-deck 16（絶対確定）。探索が
  ランダム5に過適合しても、より広い gate/eval-deck が昇格前に検出する。すべて実メタで一貫。
- **実測での訂正（2026-07-09）**: `time make ratchet-nn RATCHET_ITERS=15` = **1063分**（17.7h・gate 途中で停止）。
  分解すると **league ≈ 約64分/iter**（当初 ~21分見積もりは**3倍楽観**＝低スペックの1試合 ~8-11秒を過小評価）、
  旧 gate ≈ 約2h。**探索が律速**。→ overnight iters を 15→**7**（≈8h）に、無印(3)は≈3.5h と現実化。
- **gate の2プロファイル分離（実測を受けて）**: ① `make champion-gate`＝単独・厳格（相手12・16試合・約1〜1.5h）
  ② ratchet 内蔵 gate＝毎サイクル・軽量（相手6・12試合・約30〜45分）。**floor は 4→0**（相対判定で相殺・
  重さの本体＝終端ロールアウトを除去＝最大の効き）。両者とも確認評価は残す。eval-deck は提出忠実(64/8・16)のまま。
- **成果の実証（ratchet 初成功）**: 実メタランダム探索の出力が gate 初 eval で **new 最悪0.250/平均0.481 >>
  best 最悪0.100/平均0.390**＝実メタ相手に明確に上回る候補を生成（§27 の狙い＝探索を実メタにが機能）。
- 全て Makefile 変数で上書き可（SEARCH_SAMPLE/SEARCH_SIMS/GATE_OPPS/GATE_GAMES/RN_GATE_OPPS/RN_GATE_GAMES/GATE_FLOOR）。

## 28. Docker は「使い捨て（run --rm）」のまま — 持続コンテナにしない
- **問い**: `make` の各 Docker ターゲットは `docker compose run --rm dev <cmd>`＝毎回コンテナを生成・破棄する。
  一度 `up` して `exec` で叩く持続コンテナにまとめた方が速いのでは？
- **判断: 使い捨てのまま**。この構成では持続の利点がほぼ無く、むしろ欠点が出る。
- **なぜ利点が出ないか**:
  1. **起動回数が少ない**: ratchet-nn 1回で `run` は league（全 iter を1コンテナ内でループ）＋ gate の**2回だけ**。
     overnight（5〜6h）でも起動2回＝数時間に対し生成オーバーヘッド（〜1〜3秒）は誤差。
  2. **状態はホスト側マウントで永続**: `compose.yaml` が `.:/workspace`・`data`・`models` をバインドマウント。
     checkpoint やモデルは**コンテナでなくホストのファイル**に残る＝使い捨て間で resume が効く（league→gate で実証）。
     持続にしてもここは何も改善しない。
  3. **遅さの実体は torch import でプロセス単位**: `exec` でも `python` 起動ごとに発生。持続で減るのは
     コンテナ生成の数秒だけ。
- **むしろ使い捨てが良い理由（特に low-spec）**: ①コマンド後に RAM/GPU を解放（持続は常時抱える）②`make build`
  後に常に最新イメージを使う（持続は再起動まで stale）③up/down のライフサイクル管理不要 ④長い処理と別コマンドを
  独立起動できる（並行に強い）。
- **持続が効くのは「短いコマンドを高速に何十回も叩く」時だけ**＝この repo は軽い作業（lint/test/smoke）を
  **ホスト Python** に振り分け済み（Makefile の住み分け）ので該当しない。対話的に温めたい時は `make shell`。
- **既知の小不整合（未修正・任意）**: `make up` で持続 dev を起動しても `make exec` は `run --rm`（別の使い捨て）を
  使い up 済みコンテナを活用しない。rapid な対話デバッグを多用するなら「dev が up 中なら `compose exec`」へ賢化する
  余地はあるが、バッチ運用には不要なので現状維持。

## 29. 「0枚負け」の真因 — エネ加速ゼロ＋操縦の打ち回し欠落（ロール注入で対処）
- **実戦 replay の深掘り（分類でなくサイド差）**: nn の敗北29試合中 **16試合がサイド0枚**（自分が取れた
  サイド平均 0.7/6・ismcts は 1.5）。「僅差で競り負け」でなく**何もできず一方的に轢かれる**。しかも0枚負けは
  相手14デッキに分散＝**特定相性でなく汎用的な立ち上がり不全**。＝敗因分類の「その他」の正体（最終観測が
  終局を数手取りこぼす近似ラベルで、中身は「立ち上がれず殴られ負け」）。
- **構成の機能ロール分解で真因判明**: COMP_BOUNDS（poke/item/sup/…）は帯内だが、効果ロールで見ると
  **draw/search 17枚・energy_accel（展開）0枚**。アタッカーは 340HP・270打点の大型（要多エネ）なのに
  **加速ゼロ＝手貼り1枚/ターンでしか起動できず遅すぎる** → 速い実メタに轢かれる。energy_accel カテゴリは
  メタ全体で健全（特性/トレーナー24件）＝分類バグでなく本物の欠落。
- **根本原因＝凍結nnのテンポ盲目による共適応ロック**: ①COMP_BOUNDS が機能ロールを縛らない ②判定する
  凍結nnがテンポ/展開を評価できない（board-blind・§24）→「遅い」を罰せず、加速ゼロの遅いデッキへ収束。
  共適応ロックの新形態（操縦がテンポ音痴→テンポ不問デッキへ）。
- **対策1（デッキ）: 機能ロールの下限を注入**（`deck.MIN_ACCEL=2`・repair_composition）。実メタ頻出の加速
  トレーナーを**同カテゴリの冗長札と入れ替え**て最低枚数を強制（カテゴリ枚数は不変＝帯を崩さない）。
  §24 の「学べない知識は検証済み事前分布として注入」のデッキ版。検証: champion_best 加速0→2（60枚合法）。
- **対策2（操縦）: 打ち回しの順序を実装**（agents `_choose_main`）。①draw/search/**加速**（掘る＆エネ伸ばす）
  → ②進化 → ③**どうぐ装着** → ④エネ付与 → ⑤ベンチ → ⑥**スタジアム（場に無い時だけ）** → ⑦攻撃。
  **加速札を入れても操縦が打たねば腐る**ため両者は不可分。ABILITY/TOOL_CARD/PLAY を効果マスクで判定。
  検証: 加速注入デッキで6局→**加速札を14回プレイ**（連結が実戦で機能）。
- **凍結nnへの波及**: 提出は floored NN（floor=ヒューリスティック rollout の接地）。**heuristic を強くすると
  全 pilot の床が上がる**（floored NN・ISMCTS の rollout）。＝NN 再学習せずに操縦を底上げできる
  （凍結の制約下での「操縦の再学習」の代替）。
- **次**: この repair＋heuristic で ratchet を再探索（加速入りの速いデッキが探索される）。実戦 A/B で
  0枚負けが減るかを追跡（弱点シフトの検証）。
- **落とし穴（実測で判明・重要）**: 高速化で `GATE_FLOOR=0` にしたら、**gate の pilot が凍結nnだけになり
  加速を打たない**（加速を打つのは floor 経由の改良ヒューリスティック）。→ 加速デッキの利点が gate に
  見えず昇格できない・提出(floor8)ともミスマッチ。**floor は「pilot≥heuristic の接地」だけでなく
  「改良ヒューリスティックの手（加速/どうぐ）を実際に打たせる経路」でもある**。判定を軽くする時に
  floor を削ると、ヒューリスティック改良が全て無効化される。→ 教訓を受けて次項の構造変更。
- **構造変更: ratchet から gate を分離**（2026-07-10）。ratchet＝探索のみ（best を種に→champion_deck 出力）、
  昇格は **make champion-gate を随時**実行。利点: ①探索ループから gate の固定尾が消え **iter を稼げる**
  ②gate が毎回でなく随時なので **floor8（提出忠実・加速を打つ）に戻せる**（重くてよい）。探索は floor 不要
  （repair が全候補に加速を強制注入するので、floor 付き gate/eval-deck が正しく評価する）。

## 29b. 加速注入の実戦検証（1日目）— デッキ側仮説は不支持・機構は機能
- **検証設計が機能した例**: 同一新デッキ（加速入り昇格 best・全108試合で使用を replay から確認）に
  両操縦を載せた純粋な操縦 A/B ＋ 前日（旧デッキ）との日次比較。
- **機構は動いている**: 加速札は実戦の 63〜65% の試合で実際にプレイされた（終局捨て札から検出）＝
  「注入→操縦が打つ」の連結は本番でも機能。
- **だが結果は動かず（仮説不支持）**: 勝率 nn 0.373 / ismcts 0.421（前日 0.408/0.455 と同帯）。
  **0枚負け率 59%/58%・平均獲得サイド 0.7/1.0 で不変**。ベンチ切れ敗因比も戻った（nn 66%）。
  条件付き勝率も「加速を打った試合の方が良い」を示さない（nn 0.375 vs 0.368・ismcts 0.351 vs **0.550**）。
  → **「加速ゼロが0枚負けの主因」というデッキ側仮説は実戦で棄却方向**。§29 の操縦側改良
  （打ち回し順序）は教師強化として引き続き有効（floor/ISMCTS rollout の底上げ）。
- **示唆**: ①注入は tool 1種×2枚＝用量/質が不足の可能性はあるが、条件付き勝率が負なので
  盲目的な増量はしない。②0枚負けが両操縦で 19/19 と同一＝**操縦でなくデッキ/マッチアップ駆動**。
  頻出相手デッキ別成績: 2位 0.29(17戦)・3位 0.27(11戦)＝**頻出アーキタイプに構造的に轢かれている**。
- **次の仮説（低コスト・高情報）**: 進化探索の自作デッキには天井がある（判定操縦の歪み＋探索量）。
  **実メタの勝ち組デッキをそのまま自デッキ候補として測る（ネットデッキ検証）**——我々に勝率 0.7 超の
  頻出デッキ（例: 04621784・a8c57d4b）を eval-deck にかけ、best を上回るなら gate 経由で昇格。
  実メタ 191 デッキと対戦成績ログは既にあり、メタの淘汰圧を借りる方が探索より速い可能性。

## 31. 差をつける推論時レバー2本 — 適応 sims・操縦の残り穴（にげる/昇格）
- **背景**: ネットデッキ（§29b）は他参加者も辿り着く＝土俵に上がるだけで中位止まり。差は
  「操縦の性能」から出る。replay 実測が示した未使用資源: **NN 提出は 600 秒中 ~550 秒を残していた**
  （ismcts は 62 秒まで使い切る）＝推論時間という全員平等の計算資源を9割捨てていた。
- **①適応探索（時間で考える NN-MCTS）**: `make_nn_mcts_agent(game_budget=...)` で有効化。自前時計＋
  「1sim×1det の単価 EMA（floor 込み）」から `plan_search` が今手の **(sims, dets)** を配分
  （残り予算 ÷ 残り決定数見込み・床=従来 64×2・天井 512×16・終盤の使い切り防止に残り決定数の床 8）。
  **dets（決定化の幅）優先**で配る: この net は sims 32≈64 で深さ飽和の実測があり、不完全情報では
  決定化平均（PIMC）の分散低減＝§26 ベイズ相手推定の多サンプル化の方が効くため。**提出のみ有効**
  （eval/gate は budget を渡さない＝固定・測定時間が爆発しない）。
- **①の検証で分かったこと（プローブの効用ふたたび）**: smoke の見かけ（max 0.3〜0.6s/手）が「発火せず」に
  見えたが、plan_search をスパイすると **(64,2)→(141,4)→(152,5)→(129,8)→(130,11) と正しくエスカレート**
  していた。真相＝この net の1評価は ~0.1ms と安く、単価 EMA が下がり続けて配分が拡大するランプ中だった。
  収束後は旧 128 units → cap 8192 units＝**1手あたり64倍の探索量**。単価は実測ベースなので、遅い提出
  環境でも自己適応してクロック超過しない（60s 予算 smoke で 2.2s/21手＝安全側も確認）。
- **②操縦の残り穴（floor が上がれば floored NN・ISMCTS rollout・蒸留教師の全部が上がる）**:
  - **にげる**: 従来 RETREAT を一切使わず「詰み active」のまま殴られ続けていた。保守条件
    （攻撃不能 かつ ベンチのエネ > active のエネ）でのみ交代＝にげるコストの浪費を防ぐ。
  - **昇格/交代先（TO_ACTIVE/SWITCH）**: 従来は**先頭固定**＝KO 後に空のたねを前に出していた。
    エネ最多→HP 残でランク付け（攻撃できる子を前に＝サイドレース直結）。
- **検証が実バグを捕獲（教訓）**: 昇格ランクの初版は option の `inPlayArea/inPlayIndex` で解決したが、
  E2E プローブで「9回発火・全て旧既定と同じ」→ フィールドをダンプすると**エンジンは `index` に
  ベンチ位置を入れ inPlayArea は None**＝解決が常に失敗する no-op だった。`index` ベースに修正後、
  21回中（ベンチに差がある13局面で）6回が旧既定と違う選択＝機能を実測確認。
  **「テストが通る」と「本番の形のデータで動く」は別**——実データの形をダンプして確認する作法。
- 判定: bench 回帰 0.910（劣化なし）・全52テスト green。実戦効果は次の提出 A/B で測る。

## 33. リーダーボード諜報と1位の方策クローン（デッキと操縦のセット借用）
- **発見（ユーザー）**: リーダーボードから**他チームの replay を DL できる**＝全参加者が無償アクセス可能な

  §32 の「思考時間＝差」仮説は頂点では不成立＝**強さの源泉はデッキ＋高速で堅い方策**。
  → 探索量（cap 増し）より**方策の質**へ投資、の裏づけ。
- **共適応の実測（ユーザーの予見どおり）**: 1位デッキ×我々の操縦 = **0.537/0.100** ＜ 現 champion

## 34. Kaggle 提出枠の仕様と A/B 運用（実地で判明・恒久ノウハウ）
- **アクティブ提出は「最新2つ」**: 3つ目を提出すると**最古が自動で落ちる**。狙った2構成を並走させるには
  **提出順で制御**する（残したい構成を後に出す）。今回は teacher → ismcts の順で {teacher, ismcts} を実現。
- **再提出はレートがリセット**（同一 tar でも新規エージェント扱い・数日かけたクライムを失う）。
  ただし逆手に取れば**2構成の同時スタート＝公平な paired A/B** になる（レート差・遭遇帯差の交絡を除去）。
- **提出物の再ビルドは「ついで強化」の機会**: 同梱物（§26 相手推定プール等）は日々成長するので、
  枠を動かす時は必ず `make submission*` で作り直す（今回 79→262 デッキに無料強化）。
- **replay の A/B ラベルはフォルダ名**（data/replays/<variant>/）。新変種はフォルダを増やすだけ。
- **teacher 12h 中間（暫定・確定は1日データで）**: クローン枠は ismcts 枠より劣勢。ローカル判定
  （0.777 vs 0.588）と同じ向き＝**eval-deck の両席操縦交絡は結論を覆すほどではなかった**可能性
  ＝ローカル floor8/20試合プロトコルの信頼度が上がった（判定を早く・安くできる較正情報）。
- **事前登録した分解計画（1日データで実施・後知恵バイアス防止）**: teacher の負け方を3仮説で分類——
  ①**OOD大ポカ型**（floor0 の安全弁なし・短手数/0枚負け多発）→ floor4 で再提出
  ②**ライン切れ型**（一致率47%でコンボの線が切れる・手数が1位の対局と乖離）→ クローン継ぎ足し
  ③**相性型**（特定相手に集中負け・c921b9b2 が我々の帯に不適合）→ 撤退し nn-operative 枠へ差し戻し。

## 現在地と次の判断（2026-07-07）
- **提出（Kaggle・3枠並走中）**: ①ISMCTS ②floored NN＋盤面補正α0.2（エネ33チャンピオン）
  ③同（実メタ構成の repaired デッキ）。実戦成績: nn 0.464 > ismcts 0.395、nn_repaired は初期 n=18 で
  0.333 だが**ベンチ切れ負け 63%→25%**＝故障モードは狙い通り修正（耐久を勝ちに変換できるかが焦点）。
- **原因究明の遷移（この判断ログの本筋）**: 「NN が学ばない」の真因を段階的に切り分けてきた:
  ①弱教師（TB=0.25）→ ②one-hot 雑音説は自己一致率 0.85 で棄却 → ③**過大容量**（right-size で解決・§14訂正）
  → ④自己蒸留の空転（根ノイズ＋fresh 種・§18）→ ⑤**EMA 凍結バグ**（per-iter に decay0.999・§22追記）
  → ⑥**self-play の z 汚染**（全手サンプリング→偽相関の学習・§23）。⑤⑥は「プラトー」に見えた期間の
  真因で、**過去の「種超え」判断は過大評価だった**と遡って訂正。対策が毎回正反対なので
  「診断で切り分けてから動く」（§21）が最重要の作法。
- **NN の現在**: 実用系は seed（旧系譜最良・v2.3 形式変換済み）＝提出中の net と同水準。v2.3（盤面特徴）
  の学習は「温度スケジュール＋収集補正OFF＋カナリア」の対策入り improve で**再検証中**。
  カナリアが再度沈むなら self-play 撤退→distill 継ぎ足しで v2.3 を学ばせる（教師固定＝安定）。
- **デッキ軸**: league は構成射影（COMP_BOUNDS・実メタ帯）内で探索する新基準に移行済み。
  ローカル評価は共適応ロックで序列を覆せないため、デッキの裁定は実戦 A/B（nn vs nn_repaired）に委任。
- **次の判断**:
  1. 対策入り improve の判定（カナリア維持＋同一 run 差分 B−A ≥ 0）→ 成立なら self-play 本格運用へ。
  2. nn_repaired の実戦 n≈50 でデッキ A/B の中間判定。
  3. どちらかで改善が確定したら最良構成（net×デッキ×注入有無）で再提出・issue #2/#4 更新。
